## 一、总体结论

工程完成度高于同类个人项目：类型系统、错误分层、SSRF 防护、自动换源状态机、进度对账都有明确设计意图，且 E2E 跑的是真实首帧而非 mock。

但存在 **4 个会直接影响正确性的缺陷**（进度错乱、搜索结果不全、请求风暴、换集误判换源），以及 **一组中等性能隐患**（播放中周期性全量重渲染、同步 localStorage 写入、GPU 特效叠加）。用户体验整体"可用且体面"，但距离"达标"缺少三类东西：播放器基础能力（倍速/字幕/画质）、设置页的可操作性、以及异常路径的视觉兜底。

**没有一整套用户体验测试。** 现有 E2E 覆盖主干 happy path，异常路径、键盘可达性、窄窗口、长时间稳定性均为空白。

## 二、P0：正确性缺陷

### 1. 换集时进度可能写入错误的集

`prototype/src/App.tsx:1750`、`1806`

```ts
episodeId: title.mediaType === 'series'
  ? (episodeIdForIndex(title, index) ?? current.episodeId)   // ← 回退到"当前集"
  : undefined,
```

`episodeIdForIndex` 用 `title.episodes`（豆瓣集数）反查。当源线路集数多于豆瓣集数（例如豆瓣标 24 集、源站给 40 集），第 25 集往后查不到 id，`??` 回退成**正在播的那一集**的 id。

后果：播第 30 集时 `playback.episodeId` 仍是第 5 集的 id，`handlePlaybackProgress` 据此落库 → 第 30 集的进度覆盖第 5 集；下次"继续观看"跳到错误集数。

这正是 AGENTS.md 里专门写过的对账机制想防的问题，但只防住了"旧集快照写到新集"，没防住"新集继承旧集 id"。

**修复**：集数映射失败时应生成稳定 id（如 `${title.id}-src${index + 1}`）而不是回退旧 id。

### 2. 搜索结果首次返回严重不全

`src-tauri/src/play.rs:22`、`1957`

```rust
const SEARCH_MERGE_WINDOW: Duration = Duration::from_millis(250);
```

任意一个源先返回可用结果后，只再等 **250ms** 就跳出循环，其余仍在途的源全部被标记为「超过搜索时限，已跳过本次结果」。前端 `searchSourceErrors` 随即显示「部分源未响应」。

实际观感：搜一个热门片，第一次只出 1~2 个源的结果，用户以为"只有这么点源"。前端在 2.8s 后会再搜一次命中后台缓存，才补齐 —— 但多数用户不会等。

**修复**：merge window 提到 800~1200ms，或改为"等所有源返回，但首屏先渲染已就绪部分"（前端已有这个能力，`publish()` 支持增量）。

### 3. 搜索无取消、无最小长度，逐字触发请求风暴

`prototype/src/App.tsx:704-812`

每个 keystroke 经 350ms 防抖后，都会触发：豆瓣 suggest + `play_search`（7 个启用源，每源最多 4 页）。即单次搜索最坏 **28 个 HTTP 请求**。快速输入 5 个字、中间停顿数次，就是上百请求。

后端有 5 分钟缓存（`SEARCH_TTL`）兜底，但不同 query 不命中；断路器阈值 3 次失败，风暴中容易误开断路器，导致后续 60s 内该源全部不可用。

**修复**：搜索前要求 ≥2 字符；用 `AbortController` 或请求序号丢弃过期结果；对同一 session 的相似 query 做前缀复用。

### 4. 长时间播放后换集被误判为"源失败"

`src-tauri/src/play.rs:29`、`2037`

`play_resolve` 只读 `cached_detail`，而 detail 缓存 TTL 为 1800s（30 分钟）。前端 `resolveSession` 在换集时传 `options.detail`（内存里的旧对象），走 `resolveFromDetail` → 调 `play_resolve` → 后端缓存已过期 → 返回「详情尚未加载，请先调用 play_detail」。

`beginPlayback` 的 catch 会把它当普通失败处理 → `onSourceFailure` → 冷却该源 60s → 自动换源。

后果：看完一集（45 分钟）自动连播下一集时，明明源是好的，却触发换源 + toast「已切换到 XX 源」，起播多等十几秒。

**修复**：`play_resolve` 在缓存缺失时回源一次（或前端换集时先 `playDetail` 预热）；把"缓存缺失"与"源不可用"区分成不同错误码。

## 三、P1：性能隐患

| # | 位置 | 问题 | 影响 |
|---|---|---|---|
| 5 | `Theater.tsx:1015` + `lib.ts:36` | 音量滑块每次 `onChange` 都 `JSON.stringify` + 同步 `localStorage.setItem` | 拖动时每帧一次同步磁盘 IO，低端机可感知卡顿 |
| 6 | `App.tsx:1546` | 播放中每 5s `setPlayback` 更新 `current` → `progressFor` 引用变化 → `BrowseView` 全量重渲染 | 瀑布流 300+ 卡片时每 5 秒一次全量 diff，且此时 Theater 正覆盖在上面 |
| 7 | `useHlsPlayer.ts:318` + `Theater.tsx` | `timeupdate` 每秒 `setTime` → 整个 Theater（1234 行，含最多 200 项剧集列表）重渲染 | 剧集抽屉打开时每秒重建 200 个节点 |
| 8 | `styles.css` | 32 处 `backdrop-filter`、31 处 `blur()`，配合 `transparent: true` 无边框窗口 | WebView2 透明窗口下 backdrop-filter 需读回背景，与视频解码叠加，低端 GPU 掉帧 |
| 9 | `BrowseView.tsx:406`、`App.tsx:412` | 无限滚动常驻 1200ms 轮询；每次追加都全量 `readFeedCache()` 解析 + 重写全部分类 | 滚动期间持续 GC 压力；缓存到 2000+ id 后每次几十 KB 序列化 |
| 10 | 全项目 | `<img>` **0 处 `onError`**，无占位图 | 豆瓣图床抖动时整屏黑块，无任何提示 |
| 11 | `play_proxy.rs:1073` | 上游不支持 Range 的 MP4（返回 200 + 全长）→ `length > 64MB` 直接 502 | 这类源永久不可播，无降级路径 |

补充：`play_proxy.rs:1107` 对 **206 分段响应**也返回 `Cache-Control: public, max-age=3600`。同一 URL 不同 Range 的响应带可缓存头，理论上存在 WebView2 分段缓存串号风险，建议分段响应改 `no-store`。

## 四、P2：体验与防呆

### 已做对的（不必改）

- i18n 用 `Record<MessageKey, string>` 强制双语完整 —— tsc 通过即证明字典无缺口，比人工维护可靠。
- 换集进度快照按 `episodeId` 对账，页面隐藏/关闭时 flush，防丢最后 5 秒。
- 自动换源三层触发（启动无帧 3s 代理重试 → 进度感知延长 → 换线/源；单次冻结 60s；5 分钟内 3 次 >1s 真实卡顿），亚秒抖动与 seek 引起的不计数。
- SSRF 双层：`ensure_public_host` 预检 + `PublicDnsResolver` 连接层逐 IP 校验，关闭 DNS rebinding 窗口。
- 广告过滤有 `max_drop_ratio` 30% 兜底，超限整体放弃而不是误删正片。
- 代理 token 每次启动随机；播放源 key 白名单校验；标题缓存 2MB 预算 + 片单条目 pinned 保护。
- Escape 分层关闭、`/` 聚焦搜索、播放器全套快捷键、`prefers-reduced-motion`。

### 缺失的防呆

| 问题 | 证据 | 建议 |
|---|---|---|
| toast 永远显示 ✓ | `App.tsx:2396` 硬编码 `<Check>` | 「部分源失败」「该线路仅网页」「集数被钳制」都是警告，却配对勾图标，语义错误 |
| 单击暂停延迟 250ms | `Theater.tsx:707` | 用户点一下要等 250ms 才有反应，观感像"没点上" |
| 无续播提示 | `App.tsx:1474` | 静默从上次位置开始，用户会以为"怎么从中间开始" |
| 无骨架屏 | `BrowseView.tsx:474` | 首屏只有 spinner，瀑布流场景应给 8~12 个占位卡 |
| 单实例无锁 | `main.rs` 未引入 single-instance | 双开共享同一 localStorage，进度/片单互相覆盖 |
| 无窗口尺寸记忆 | `tauri.conf.json` 固定 1292×864 | 每次启动回到默认大小 |
| 设置页只读 | `BrowseView.tsx:237-261` | 播放源只能看不能启用/禁用；无「清空缓存/片单/进度」 |
| 只有 1 部片时 hero 重复 | `App.tsx:2194` | `(index*2+3) % length` 会取到 featured 自己，右侧出现两张同片卡 |

### 功能缺口（影响"达标"判断）

- **无倍速播放**（全项目 0 处 `playbackRate`）
- **无字幕控制**（0 处 `<track>`；HLS 的 `EXT-X-MEDIA` URI 会被代理重写，但无 UI 可切换/关闭）
- **无画质选择**，硬编码 1080P 上限（`useHlsPlayer.ts:566`），4K 屏用户无法解锁
- 无跳过片头/片尾、无音轨选择、无画中画

## 五、测试覆盖评估

**单测（33 个）**：只覆盖纯逻辑（名称匹配、候选评分、集数映射、代理 URI 解析、广告过滤规则）。这层做得扎实，`unique_test_key` 这类并发污染问题也考虑到了。

**E2E（4 脚本 / 12 断言，上次全绿）**：首页渲染、无限滚动追加（100→150）、搜索、详情、真实首帧（1080P / 7018s）、token 校验、空格暂停、进度落库、CSP、JS 异常。这条链是真实有效的，不是假绿。

**空白区**：

1. 异常路径 —— 断网、全源失败、代理 403、豆瓣超时、缓存被裁剪，全部未覆盖
2. 键盘可达性 —— Tab 遍历顺序、焦点可见性、focus trap 边界、`/` 在抽屉关闭时的行为
3. 窗口 —— 最小尺寸 1000×640 下的布局、缩放、沉浸模式进出
4. 状态迁移 —— 片单/稍后看/最近观看的增删、语言切换后文案完整性
5. 长时稳定性 —— 连续播放 2 小时的内存曲线、换源 10 次后的句柄泄漏
6. 播放器交互 —— 拖动进度条、滚轮调音量、双击全屏、剧集抽屉拖拽（后者有专门脚本，前者没有）

**结论**：做了"主干冒烟测试"，没做"完整体验测试"。以当前覆盖面，可以说"核心链路可回归"，不能说"用户体验已验收"。

**性能目标（建议写入验收）：**

- 播放 10 分钟，Theater render 次数 ≤ 600（当前按 4/s 约 2400+）。

- 连续播放 1 小时，内存增长 ≤20%，无持续句柄增长。
- 图片同 URL 并发请求只回源 1 次；代理单请求内存 ≤ 上限 + 缓冲余量。

## 8. 仍待确认 / 风险

- **性能数字**：P-01/P-02 的收益是代码路径推导，需用 Performance/内存采样确认；不要仅凭主观“更顺”。

### 10.1 测试中发现的额外问题

- **robustness 空搜索**：新增搜索错误态使用 `role="alert"`，旧脚本把它当成 ErrorBoundary 崩溃；已把“崩溃”判定改为 ErrorBoundary 文案，错误态本身是预期 UI。
- **robustness 倍速**：视频 metadata 未就绪时点击倍速，下一次 load 会重置 playbackRate；产品最终会恢复 `rateRef`，测试改为等 `readyState>=2` 后再断言。
- **B1 旧断言**：每集独立续播上线后，“新集必须从 0 开始”不再成立；断言改为“保存值不超过新集实际起点+15s，且 episodeId 已切换”，仍能抓住旧集进度泄漏。
- **PiP**：真实 WebView2 中 `document.pictureInPictureEnabled` 为 true，但 `requestPictureInPicture()` 后 `pictureInPictureElement` 仍为空；按钮是无效果假功能，已移除。
- **画质**：真实源均为单 level，`.quality-select` 按预期隐藏；多码率源的档位切换仍需专门源验证。
- **下载弹窗**：已修复。导出备份不再使用 Blob + `<a download>`，改为 Rust `export_backup` 直接写系统下载目录；真实 E2E 读取 `data-export-path` 并校验文件内容/删除测试文件，全程不出现 WebView2 下载提示。
